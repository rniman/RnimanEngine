# 개발 목표와 순서

[README](../README.md) · [현재 모델 계약](static-model.md)

D3D12 기반 미니 게임 엔진을 실제 데모와 함께 개발한다. 사용할 곳이 생기는 순서로 기능을 추가하고, 각 단계에서 실행 가능한 결과를 유지한다.

## M02 완료 범위

단일 메시·Submesh·재질 로딩 → GPU 업로드 → Phong 렌더링 → ImGui 편집을 연결했다. 지원 범위와 에셋 준비는 [정적 모델 계약](static-model.md)을 따른다.

## M03 동적 오브젝트 관리

목표는 로딩된 Cube·Sphere·Helmet을 원하는 개수만큼 배치하고 각각 선택·편집·삭제하는 것이다. 아래는 구현할 기본안이며 아직 코드에 적용하지 않았다. 초기 화면은 현재 세 인스턴스를 유지한다.

### 사용 흐름

1. `Create model`에서 모델을 고르고 `Create`를 누른다. 새 오브젝트를 즉시 선택한다.
2. 목록은 `Object <ID> - <모델 이름>`으로 표시한다. 같은 모델도 개별 항목으로 구분한다.
3. 선택한 오브젝트의 위치·회전·Scale과 자동 회전을 편집한다. 회전 편집 시 자동 회전 정지 등 기존 동작을 유지한다.
4. `Delete selected`는 선택한 오브젝트만 삭제하고 선택을 해제한다. 선택이 없으면 삭제·Transform 편집을 비활성화한다.
5. 모두 삭제해도 배경·도구·카메라·조명은 유지되며 다시 생성할 수 있다.

새 인스턴스는 모델 파일의 Transform으로 생성하고 자동 회전은 끈다. 같은 위치에 반복 생성하면 겹칠 수 있으며 위치 편집으로 옮긴다. 초기 세 인스턴스의 데모 배치·회전 설정은 별도로 유지한다.

### 데이터와 책임

클래스 추가는 독립적인 소유권·불변 조건·동작을 묶을 필요가 있을 때만 한다. App의 코드 양을 줄이기 위한 `SandboxScene`·`SandboxTools`는 선행 추가하지 않는다. 상태 없는 UI 그리기·에셋 준비·렌더 데이터 변환은 함수로 정리하고, 필요하면 구현 파일만 나눈다.

| 위치 | 역할 |
|---|---|
| 오브젝트 목록 | 우선 App이 `std::vector`로 소유. 생성·삭제·ID 조회는 작은 함수로 모으고 자동 회전은 기존 갱신 경로에 유지 |
| 오브젝트 값 | 64비트 ID, 모델 번호, Transform, 자동 회전 축·속도·활성 상태, 기존 SandboxRotation 편집값. 상속·컴포넌트 체계 없이 시작 |
| `SandboxApp` | 선택 ID, 생성할 모델 번호, ImGui 조작과 오류 표시. 오브젝트의 편집 복사본을 유효성 검사 후 반영 |
| 모델 정보 | 모델 이름·통계·기본 Transform을 모델 번호로 조회. 인스턴스 수와 독립적으로 유지 |
| 렌더 데이터 | App이 장면을 순회해 변환 상수와 모델 번호를 같은 순서의 재사용 가능한 vector에 수집 |
| `D3D12Renderer` | 기존 모델별 GPU 자원을 소유하고 전달된 인스턴스를 그리는 역할 유지 |

ID는 1부터 단조 증가시키고 실행 중 재사용하지 않는다. 선택은 배열 인덱스 대신 선택적 ID로 보관하며, 삭제·재할당을 넘어 요소의 포인터·참조를 저장하지 않는다. 작은 목록에서는 ID를 선형 탐색한다. ID 소진·잘못된 모델 번호는 생성 실패로 처리하고 기존 장면을 유지한다.

기존 SandboxRotation은 ImGui에 의존하지 않는 값이므로 오브젝트와 함께 보관한다. 선택을 바꿨다가 돌아와도 370° 같은 편집값을 유지하며, 오브젝트 삭제 시 함께 제거한다. 저장된 회전의 기준은 Transform의 Quaternion이다.

### 프레임과 자원 수명

`입력·카메라·조명·장면 갱신 → UI 편집·생성/삭제 요청 → UI 순회 종료 후 요청 적용 → 렌더 데이터 수집 → 그리기`

현재 갱신 순서를 유지하므로 UI에서 편집한 회전이 같은 프레임의 자동 회전으로 덮이지 않는다. 생성은 그 프레임부터 표시하고, 삭제는 그 프레임의 그리기에서 제외한다. 자동 회전 재개는 다음 갱신부터 진행하며 정지 중 시간은 누적하지 않는다. 요청은 App 내부의 한 프레임 데이터로 처리하고 범용 명령 시스템은 만들지 않는다.

모델 파일·이미지는 시작할 때 한 번 읽고 GPU에 올린다. 생성·삭제는 CPU 인스턴스만 바꾸므로 메시·텍스처를 재업로드하거나 해제하지 않는다. 렌더러의 기존 빈 목록 처리와 Fence 이후 상수 버퍼 확장을 사용한다. 빈 장면에서도 초기화된 모델 자원은 종료까지 유지한다.

### 구현 순서와 완료 범위

각 단계는 빌드·실행 가능한 변경 단위로 진행한다. 구현은 기존 Sandbox 프로젝트에서 이어가며 주 변경 파일은 `SandboxApp.h/.cpp`다.

#### 1. 식별·저장 정리

- `ModelInstance`에 `std::uint64_t` ID와 `std::size_t` 모델 번호를 추가하고 `mObjects`를 `std::vector<ModelInstance>`로 바꾼다. 초기 ID는 1~3, 모델 번호는 0~2로 대응시킨다.
- `ModelInfo`에 모델 이름·파일의 기본 Transform을 보관한다. 모델 정보의 크기는 로딩할 모델 수에서 정하고 `INITIAL_OBJECTS.size()`와의 결합을 없앤다. 초기 데모 배치와 새 인스턴스의 기본값을 분리한다.
- `mSelectedObject`를 선택적 ID로 바꾸고 ID 조회 함수를 둔다. 목록 선택 후 해당 ID를 다시 조회해 편집하며, 모델 이름·통계는 찾은 오브젝트의 모델 번호로 읽는다. 선택 없음도 처리한다.
- 초기 Cube의 파일 Transform, Sphere·Helmet의 데모 배치·회전 설정과 각 오브젝트의 Euler 편집값을 유지한다. 자동 회전은 기존 순회를 사용한다.

이 단계에서는 초기 세 인스턴스만 사용하고 기존 고정 렌더 입력을 유지한다. 생성·삭제는 3단계에서 연결한다.

#### 2. 렌더 경로 변경

- `Render()`의 고정 상수 배열과 `{0,1,2}`를 재사용 가능한 두 vector로 바꾼다. 매 프레임 내용을 비우고 현재 오브젝트 수에 맞춰 용량을 확보한다.
- 오브젝트를 한 번 순회하며 변환 상수와 해당 모델 번호를 같은 순서로 추가한다. 변환 상수 생성 실패 시 오브젝트 ID·모델 번호를 포함해 원인을 알리고 그 프레임의 렌더링을 중단한다.
- 두 목록을 기존 `D3D12Renderer::Render()`에 전달한다. 빈 목록도 전달해 배경·ImGui·Present를 유지하고, GPU 상수 버퍼 확장은 기존 Fence 대기 이후 경로를 사용한다.
- 기존 `RendererSmoke`의 다중 모델 검사에 소수 인스턴스 → 0개 → 기존 용량 초과 → 감소 흐름과 같은 모델 번호 반복을 보강한다.

UI는 아직 초기 세 인스턴스를 표시한다.

#### 3. 생성·삭제 UI 연결

- App 내부에 생성·삭제 함수를 둔다. 생성은 모델 번호·ID 소진을 먼저 검사하고 값 구성을 마친 뒤 목록에 추가한다. 성공한 새 ID를 선택하며 실패는 생성 요청 적용 직전의 목록·선택을 유지하고 원인을 표시한다.
- 새 인스턴스는 모델의 기본 Transform, 꺼진 자동 회전, 새 회전 편집 상태로 시작한다. 이후 `Auto rotate`를 켤 수 있도록 회전축·속도는 해당 모델의 초기 데모 설정을 사용한다.
- `Create model`·`Create`·`Delete selected`를 추가한다. 버튼은 모델 번호나 삭제할 ID만 한 프레임 요청으로 남기고, 목록 순회와 Transform 편집 중에는 vector를 변경하지 않는다.
- `Run()`에서 `DrawTools()`·`mGui.EndFrame()` 이후, `Render()` 이전에 요청을 적용한다. 같은 프레임에 두 요청이 있으면 요청한 ID 삭제 후 생성 순서로 처리하고 새 오브젝트를 선택한다. 처리한 요청은 비운다.
- 삭제는 ID로 대상을 찾아 순서를 유지하며 제거하고 선택을 해제한다. 선택이 없으면 삭제·Transform 편집을 비활성화하되 생성·카메라·조명 UI는 계속 제공한다.
- README의 현재 상태·개발 UI와 설계 문서의 프레임 흐름을 구현된 동작에 맞춘다.

완료 범위는 같은 모델의 독립 편집, 중간 요소 삭제 후 남은 ID·Transform 보존, 전체 삭제 후 재생성, 반복 생성·삭제 중 리사이즈·종료다. 렌더 입력의 개수 변화는 기존 RendererSmoke에서, App 내부의 목록·선택·편집 흐름은 Sandbox에서 다룬다.

씬 저장·불러오기, 복제·Undo, 화면 클릭 선택, 계층, 실행 중 모델 자원 추가·삭제와 ECS는 이번 범위에서 제외한다.

목록의 수명·ID 발급·변경 규칙을 여러 호출부에서 중복 관리하게 되면 그 책임만 독립 타입으로 추출한다. 이름과 소속은 실제 역할·의존성으로 정하며, App 전용 보조 클래스나 Engine의 범용 Scene을 미리 만들지 않는다. ECS 비교나 다른 데모에서 재사용할 동작이 드러날 때 Engine 이동·공통 인터페이스를 검토한다. 기존 Camera·Lighting·Gui·Rotation은 이번 기능에 필요한 변경만 한다.

## ECS 비교와 후속 선택

일반 오브젝트와 같은 동작을 ECS로 구현하고 UI·렌더러를 공유한다. 동일 초기 상태·입력·경과 시간에서 변환과 렌더링 결과를 확인한 뒤, 같은 개체 수·작업량·Release 구성에서 갱신과 렌더 데이터 수집 비용을 구분해 반복 측정한다. 저장 방식·핸들 재사용·참조 무효화·순회 중 구조 변경 정책은 구현 단계에서 정한다. 측정 전 성능 우위를 가정하지 않는다.

계층 모델은 실제 다중 노드 에셋을 도입할 때 부모 관계·로컬 변환·메시 참조를 보존하고 World 행렬을 계산해 노드별로 그리는 방향으로 검토한다. 합성 World를 단일 TRS로 다시 분해하는 현재 제한을 이때 해소한다. 다중 재질·재질별 UV·텍스처 식별은 실제 에셋 요구에 맞춰 확장한다.

스켈레톤·애니메이션, 그림자·IBL·후처리, 다른 그래픽스 API, 물리·AI·오디오·멀티스레딩·독립 에디터는 사용하는 데모가 생길 때 추가한다. Engine 라이브러리 분리는 독립 빌드·재사용 수요가 생길 때 결정한다.
