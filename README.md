# Rniman Engine

D3D12 기반의 미니 게임 엔진. 장면 구성, 입력, 게임 로직, 렌더링과 리소스 로딩을 연결하여 작은 게임과 그래픽 실험에 사용한다. 각 시스템의 역할과 데이터 흐름을 직접 이해하고 설명할 수 있는 크기로 개발한다.

## 현재 상태

2026-09-15 기준 초기 프로젝트 설정 단계다. Visual Studio 솔루션과 `Sandbox` 실행 프로젝트를 생성하고 x64 기본 설정을 적용했다. PCH와 Win32 최소 창을 구현하고 x64 Debug·Release 전체 빌드 및 실행·정상 종료를 확인했다. D3D12 초기화와 삼각형 렌더링은 아직 구현하지 않았다. 아래 내용은 개발 목표와 설계 방향이며 구현 완료 목록이나 확정된 일정이 아니다.

## 목표와 범위

| 영역 | 개발 방향 |
|---|---|
| 미니 게임 엔진 | 개발 중간부터 상호작용 데모와 작은 프로젝트로 실제 사용성을 확인한다. |
| D3D12 | 주력 API로 초기화부터 리소스 관리, 명령 제출, 동기화와 화면 출력까지 구현한다. |
| ECS | 여러 엔티티와 시스템이 함께 동작하는 게임 로직에 사용하고, 일반 오브젝트 방식과 비교한다. |
| 렌더링 | 기본 Phong 조명에서 PBR까지 확장하고, 재질과 조명을 장면에서 조절한다. |
| 실시간 도구 | ImGui를 우선 후보로 카메라·Transform·조명·재질 편집과 필요한 진단 기능을 만든다. |
| 리소스 | Unity에서 씬·모델·애니메이션을 bin 파일로 익스포트하고 엔진에서 읽는다. |

D3D11·OpenGL은 비교용 확장 후보다. 초기에는 D3D12에 집중하고, 다른 구현이 필요해질 때 공통 경계를 검증한다. 모든 API의 기능 동등성이나 실행 중 교체는 초기 범위에 포함하지 않는다.

추가 렌더링, 물리, AI, 오디오, 멀티스레딩, 독립 에디터 등은 사용할 샘플과 확인할 문제가 생겼을 때 범위를 정한다.

## 개발 순서

| 단계 | 만들 것 | 완료 기준 |
|---|---|---|
| 1 | 창과 D3D12 삼각형 | 초기화·명령 제출·화면 출력·종료 흐름을 설명할 수 있다. |
| 2 | 직접 정의한 메시, 텍스처, 카메라, 기본 조명 | 여러 오브젝트를 그리고 카메라와 조명을 조절할 수 있다. |
| 3 | 일반 오브젝트 방식과 ECS | 같은 장면과 렌더러로 사용 방식과 처리 비용을 비교한다. |
| 4 | Unity 익스포터와 엔진 로더 | 메시·Transform부터 전달하고 재질·텍스처·씬 계층으로 확장한다. |
| 5 | PBR | ECS 장면에서 PBR 재질과 조명을 조절할 수 있다. |

**첫 마일스톤은 2단계까지의 데모를 문서대로 다시 실행할 수 있는 상태다.** 이후 ECS·Unity 로딩·PBR을 대표 데모에 통합하고, 스켈레톤·애니메이션은 사용하는 데모에 맞춰 추가한다. 각 단계에서 실행 가능한 결과를 유지하며 순서와 세부 구조를 조정한다.

## 설계 기준

하나의 솔루션에서 작게 시작한다. 역할과 의존성은 구분하되, 실제 필요가 생길 때 프로젝트와 라이브러리 분리를 고려한다. 새로운 추상화에는 해결할 문제와 사용 예시가 있어야 한다.

```text
입력 → 장면·게임 로직 갱신 → 렌더 데이터 수집 → D3D12 렌더러 → 화면 출력
Unity → bin → CPU 에셋 데이터 → 장면 구성 / GPU 리소스 생성
```

### 책임과 의존성

- 앱은 실행 수명주기와 엔진 구성을, 장면·ECS는 게임 상태와 갱신을 담당한다. Application·Scene과 ECS는 함께 사용할 수 있다.
- 렌더 데이터 수집 단계가 장면과 렌더러를 연결한다. 게임 로직과 ECS 저장소는 API 전용 명령 목록·디스크립터·PSO를 직접 다루지 않는다.
- 공통 렌더 데이터는 변환·카메라·조명·리소스 식별자 등으로 구성하고, 참조 대상과 유효 기간을 명확히 한다. D3D12 고유 기능은 백엔드 또는 명시적인 확장 경로에 둔다.
- 파일 파싱과 GPU 업로드를 분리하여 CPU 데이터는 렌더러 없이 검증할 수 있게 한다. 소유자와 초기화·종료 순서를 명시하고 전역 매니저로 의존성을 숨기지 않는다.
- 커스텀 할당자, 범용 매니저와 자체 분석 도구는 실제 필요에 따라 도입한다. 외부 코드는 입출력·소유권·실패 동작·버전·라이선스를 확인하고 활용한다.

### ECS

이동, 개체 생성·삭제, 컴포넌트 조합별 갱신과 Transform 계층 등 대표 작업을 먼저 정한다. 타입별 저장, sparse set, archetype 등의 선택 이유와 제약은 구현 단계에서 기록한다.

일반 오브젝트 방식과 ECS가 같은 렌더 데이터를 만드는 작은 비교 샘플을 유지한다. 두 방식의 모든 기능을 동일하게 확장할 필요는 없다. 같은 개체 수·작업량·빌드 구성에서 갱신과 렌더 데이터 수집 비용을 비교하고, 사용 편의성과 수정 부담도 확인한다.

Entity 재사용과 오래된 핸들, 컴포넌트 참조 무효화, 순회 중 구조 변경 정책을 검증한다. 시스템의 실행 순서와 읽고 쓰는 데이터를 명시하며, ECS라는 이유만으로 성능이나 병렬화 이점을 가정하지 않는다.

### 렌더링과 도구

직접 정의한 메시로 기본 조명을 확인한 뒤 PBR로 확장한다. 첫 PBR 범위의 후보는 metallic-roughness 재질과 직접광이며, IBL·그림자·후처리는 별도 단계로 검증한다.

- 좌표계, 행렬 저장·곱셈·셰이더 전달 규칙과 색 공간을 명시한다.
- GPU 작업이 끝나기 전에 리소스·업로드 메모리·디스크립터를 재사용하거나 해제하지 않는다.
- 도구 UI는 엔진의 상태 변경 경로를 사용하며 Transform 갱신 규칙과 게임 입력 처리를 우회하지 않는다.
- 지표에는 대상과 단위를 표시하고 CPU 시간, GPU 시간과 Present 대기를 구분한다. 깊은 분석에는 기존 도구도 활용한다.

### Unity 데이터 규격

메시·Transform → 재질·텍스처·씬 계층 → 스켈레톤·애니메이션 순으로 범위를 확장한다. Unity의 모든 셰이더와 컴포넌트를 재현하는 것이 아니라, 지원할 데이터와 변환 규칙을 정한다.

- 파일 식별값·버전·바이트 순서·숫자 크기·문자열 인코딩·개수·리소스 참조를 명시한다. C++ 객체 메모리를 그대로 파일 형식으로 사용하지 않는다.
- 좌표계·단위·행렬·삼각형 winding·UV·노멀·탄젠트 변환과 텍스처 저장·참조 방식을 정한다. 애니메이션 추가 시 본 인덱스·bind pose·시간 단위·샘플링 규칙도 정한다.
- 파서는 파일 범위, 크기 계산의 오버플로, 인덱스와 참조를 검사한다. 잘린 파일·미지원 버전·데이터에서 원인을 알 수 있게 실패하고 부분 로딩 자원을 정리한다.
- 작은 기준 에셋으로 데이터와 화면 결과를 비교한다. 규격 변경 시 익스포터·로더·에셋·문서를 함께 맞추고 호환 또는 재익스포트 조건을 기록한다.

## 외부 라이브러리와 도구

필요한 기능부터 도입하고 입출력, 소유권, 실패 동작을 이해하며 연결한다. 아래는 도입 계획과 후보이며, 아직 설치하거나 통합한 목록은 아니다. 실제 도입 시 버전·출처·라이선스·사용 범위와 준비 방법을 기록한다.

### 우선 도입 후보

| 구성 | 역할과 사용 범위 |
|---|---|
| [d3dx12.h](https://github.com/microsoft/DirectX-Headers) | D3D12 구조체와 반복 작업을 돕는 헬퍼. 초기화·명령 제출·동기화 흐름은 직접 구현한다. |
| [WICTextureLoader12](https://github.com/microsoft/DirectXTex/tree/main/WICTextureLoader) | 초기 데모에서 일반 이미지를 직접 로딩할 때 활용한다. DDS 변환·캐시 생성 기능과는 구분한다. |
| [DDSTextureLoader12](https://github.com/microsoft/DirectXTex/tree/main/DDSTextureLoader) | 준비된 DDS와 변환 캐시를 읽는 실행 경로에 활용한다. |
| [DirectXTex / texconv](https://github.com/microsoft/DirectXTex) | 원본 이미지의 형식 변환·압축·밉맵 생성과 DDS 저장. 변환 API를 연결할지 도구를 호출할지는 구현 시 선택한다. |
| [Dear ImGui](https://github.com/ocornut/imgui) | 개발용 상태 표시·값 편집 UI. Inspector 동작과 성능 계측은 엔진에서 구현하며, 게임 로직은 ImGui에 의존하지 않는다. |

### 필요할 때 검토할 후보

| 구성 | 검토 조건 |
|---|---|
| [DirectXMath](https://github.com/microsoft/DirectXMath) | 수학 연산 기반을 정할 때 검토한다. 필요한 타입과 연산부터 사용한다. |
| [DXC](https://github.com/microsoft/DirectXShaderCompiler) | 셰이더 빌드 경로와 대상 Shader Model을 정할 때 검토한다. |
| [MikkTSpace](https://github.com/mmikk/MikkTSpace) | 탄젠트 생성이 필요할 때 검토한다. Unity에서 내보낸 탄젠트를 사용할 수 있으면 재생성하지 않고, 노멀맵과 좌표 변환의 일치 여부를 확인한다. |
| [spdlog](https://github.com/gabime/spdlog) | 콘솔·파일 로그 관리가 필요할 때 검토한다. |
| [Tracy](https://github.com/wolfpld/tracy) | 실제 시스템의 실행 시간을 분석할 때 검토한다. |
| [D3D12 Memory Allocator](https://github.com/GPUOpen-LibrariesAndSDKs/D3D12MemoryAllocator) | 기본 GPU 자원 관리를 이해한 뒤 메모리 할당 관리가 필요할 때 검토한다. 동기화와 자원 사용 수명은 엔진이 관리한다. |
| [RmlUi](https://github.com/mikke89/RmlUi) | HUD·인벤토리·메뉴 등 플레이어용 UI가 필요할 때 검토한다. ImGui 개발 도구와 병행할 수 있다. |

모델·씬·애니메이션 입력은 Unity 익스포터와 직접 작성하는 bin 로더가 담당하며 **Assimp는 도입 대상에서 제외한다.** ECS는 직접 구현을 주력으로 하고, [EnTT](https://github.com/skypjack/entt)는 설계 참고나 비교 대상으로 둔다.

### 텍스처 변환과 캐시

초기 데모는 원본 이미지 직접 로딩으로 시작할 수 있다. 에셋 처리 단계에서는 개발 실행 중 시작·장면 로딩 시 필요한 텍스처를 변환하고, 이후 실행에서는 DDS 캐시를 재사용하는 흐름을 만든다. 플레이 도중의 동기 변환은 피한다.

```text
텍스처 요청 → 캐시 유효성 확인
               ├─ 유효 → DDS 로드 → GPU 업로드
               └─ 없음·변경 → 원본 변환·압축·밉맵 생성 → DDS 캐시 저장 → 로드
```

- DDS 자체를 캐시 파일로 사용한다. 원본 내용과 해상도·압축 형식·밉맵·색 공간 설정, 변환 도구·처리 규칙 버전을 캐시 키 또는 메타데이터에 반영한다.
- 불완전하거나 손상된 캐시는 재생성하고, 변환 실패 원인을 표시한다. 변환과 저장이 끝난 결과만 유효한 캐시로 취급한다.
- 첫 변환 비용과 이후 캐시 로딩 시간을 구분해 측정한다. 디스크 파일 크기와 GPU 메모리 사용량은 별도로 확인한다. DDS 확장자만으로 압축 여부를 판단하지 않는다.
- 최종 배포에는 미리 변환한 DDS를 준비한다. 개발용 변환 기능과 원본 파일을 배포 실행에 필수로 요구하지 않는다.
- 캐시는 재생성 가능한 산출물로 관리하고, 경로·보관·정리 정책은 구현 시 정한다. 원본과 변환 설정은 재현 가능하게 보관한다.

## 검증과 문서

대표 데모는 개별 시스템 개발 중에도 유지한다. 작은 상호작용을 일찍 넣어 엔진을 사용하는 흐름을 확인한다.

- 유지 샘플과 특정 버전으로 보존할 샘플을 구분하고, 공통 코드 변경 시 영향받는 유지 샘플을 빌드·실행한다.
- ECS 수명·삭제·쿼리, Transform 계층과 바이너리 파싱은 자동 검증 대상으로 삼는다. 화면 결과와 GPU 수명은 실행 확인과 D3D12 디버그 레이어 등으로 보완한다.
- 성능 측정에는 빌드 구성과 조건을 남긴다. 빌드·실행·시각적 확인 결과를 구분하고, 확인하지 않은 기능을 완료로 표시하지 않는다.
- 실행 방법, 코드 진입점, 데이터 흐름과 설계 이유를 기록한다. 상세 문서는 실제 구현이 구체화될 때 추가하고 같은 내용을 중복 관리하지 않는다.

**프로젝트 전용 예외·시험 적용:** 현재 없음. 필요할 때 대상 규칙, 적용 조건과 이유를 기록한다.

## 빌드와 실행

Visual Studio 프로젝트를 직접 관리하며, CMake는 필요해질 때 전환한다. [솔루션](RnimanEngine.slnx)을 열고 `Sandbox`의 x64 / Debug 또는 Release 구성을 사용한다. 솔루션과 프로젝트는 x64의 Debug·Release 구성만 유지한다.

- 확인한 설치 환경: Visual Studio Community 2026 18.10.0 (18.10.12201.205), 플랫폼 도구 집합 `v145` (MSVC `14.51.36231`), Windows SDK `10.0.26100.0`.
- x64 공통 설정: C++20, Unicode, `/utf-8`, `/W4`, `/permissive-`, `/EHsc`, Windows 서브시스템, 미리 컴파일된 헤더 사용. 경고를 오류로 처리하는 옵션은 끈다.
- 런타임 라이브러리: Debug `/MDd`, Release `/MD`.
- 출력 위치: `bin/x64/<구성>/`, 중간 산출물: `obj/Sandbox/x64/<구성>/`.
- 루트 [.editorconfig](.editorconfig)는 UTF-8 BOM 없음·LF·마지막 개행을 지정하고, C++ 파일에 탭 들여쓰기와 표시 너비 4칸을 적용한다. Markdown의 의미 있는 줄 끝 공백은 보존한다. 중괄호·포인터 배치 등은 컨벤션을 직접 따른다.

Visual Studio에서 `Sandbox`를 시작 프로젝트로 선택하고 x64 Debug 또는 Release로 빌드·실행한다. 실행 파일은 각 구성의 `bin/x64/<구성>/Sandbox.exe`에 생성되며 직접 실행도 가능하다. 현재는 배경과 제목 표시줄이 있는 Win32 창만 제공하며 외부 에셋은 필요하지 않다. 창 닫기 또는 Alt+F4로 종료한다.

### PCH와 D3D12 기본 연결

- [pch.h](Sandbox/pch.h)에 Windows·D3D12·DXGI·WRL과 기본 STL 헤더를 모은다. [pch.cpp](Sandbox/pch.cpp)는 `/Yc`로 생성하고, 이후 추가하는 `.cpp`는 첫 줄에서 `pch.h`를 include하여 `/Yu`로 사용한다.
- PCH 파일은 `$(IntDir)$(ProjectName).pch`로 구성별 분리한다. 일반 프로젝트 헤더에는 PCH를 include하지 않으며, PCH에 있더라도 직접 사용하는 의존성은 각 파일에서 include한다. 이는 채택 컨벤션의 PCH 예외 범위다.
- 프로젝트 전처리 정의에 `WIN32_LEAN_AND_MEAN`, `NOMINMAX`를 지정하여 Windows 헤더 포함 범위를 줄이고 STL의 min/max와 매크로 충돌을 피한다.
- `d3d12.lib`, `dxgi.lib`를 연결한다. 셰이더 컴파일러는 아직 선택·연결하지 않았다. 디버거 작업 디렉터리는 `Sandbox` 프로젝트 폴더로 고정한다.
- 2026-09-14 검증: x64 Debug·Release에서 PCH 생성과 `Main.cpp`의 PCH 사용(`/Yu`), 전체 컴파일·링크가 성공했다. 두 EXE에서 제목 `Rniman Engine - Sandbox`, 창 표시·응답 상태와 클라이언트 크기 1280×720을 Win32 API로 확인했다. `WM_CLOSE` 전송 후 모두 종료 코드 0으로 종료했다. 화면 캡처를 통한 시각 검증과 오류 경로의 강제 실패 검증은 수행하지 않았다.
- 검증 도중 자동 실행 환경의 `Path`·`PATH` 중복과 샌드박스의 MSBuild FileTracker 접근 거부가 발생했다. 검증 프로세스의 환경 변수 중복을 정리하고 샌드박스 밖에서 재검증했으며 프로젝트 설정으로 오류를 우회하지 않았다.

### Git 관리

- 저장소 루트는 이 README가 있는 폴더이며 초기 브랜치는 `main`이다.
- [.gitignore](.gitignore)는 Visual Studio 개인 설정·캐시, C++ 중간 파일·디버그 정보·프로파일 결과와 엔진의 빌드 출력 폴더를 제외한다. 솔루션·프로젝트·소스·문서는 버전 관리 대상이다.
- [.gitattributes](.gitattributes)는 텍스트를 LF로 정규화하며 바이너리 에셋은 줄바꿈 변환에서 제외한다. Windows 명령 스크립트(`.bat`, `.cmd`)의 체크아웃 줄바꿈은 CRLF로 지정한다. 파일 인코딩과 편집 시 포맷은 `.editorconfig`에서 관리한다.
- Unity `.meta`, OBJ 모델(`.obj`), `.bin`·DDS 에셋과 외부 라이브러리 `.lib`·`.dll`·도구 `.exe`는 전역 제외하지 않는다. `bin/`·`x64/` 같은 디렉터리도 엔진의 출력 경로에 한정해 제외한다. 재생성 가능한 에셋 캐시는 실제 저장 경로가 정해지면 해당 디렉터리를 제외한다.

### 최소 창 진입점과 빌드 명령

[Main.cpp](Sandbox/Main.cpp)의 `wWinMain` → `WindowResources::Initialize` → `GetMessageW`/`DispatchMessageW` 순서로 실행한다. 창 닫기 요청은 `WM_QUIT`로 루프를 종료하고, 지역 RAII 객체가 창 파괴 → 창 클래스 해제 순서로 정리한다. 렌더링 루프를 추가하기 전까지 메시지가 없으면 대기한다. Win32 호출 실패는 발생 API와 오류 코드를 디버그 출력·메시지 상자로 알린다.

저장소 루트의 Developer PowerShell에서 사용하는 빌드 명령은 다음과 같다. 검증에서는 아래와 동일한 인자로 설치된 MSBuild 실행 파일을 직접 호출했다.

```powershell
MSBuild.exe RnimanEngine.slnx -nologo -t:Build -p:Configuration=Debug -p:Platform=x64
MSBuild.exe RnimanEngine.slnx -nologo -t:Build -p:Configuration=Release -p:Platform=x64
```

1280×720은 초기 클라이언트 크기이며, DPI 정책·최소 창 크기·렌더러의 리사이즈 처리는 이후 창/렌더러 구현 시 정한다. 이번 단계에서는 일반 Win32 크기 조절 동작을 사용한다.

2026-09-15에 솔루션과 Sandbox 프로젝트를 저장소 루트 구조로 옮겼다. 프로젝트 상대 경로를 유지하며 출력은 루트의 `bin/`, 중간 산출물은 `obj/`를 사용한다. 이동 후 x64 Debug·Release 전체 재빌드와 각 EXE의 창 응답·닫기 후 종료 코드 0을 확인했다. 사용자가 최소 창의 화면 표시를 확인했다.
